# Mesures PERF-01

Exécuter depuis la racine du dépôt, sur la base de test autorisée et des comptes E2E identifiés. Aucun secret n'est enregistré dans les sorties. Aucun outil ne crée de compte, ne lance de migration, seed, reset, service externe ou serveur durable.

Configurer les variables du terminal : `PERF_ACCOUNTS_FILE` pointe vers un JSON privé existant, jamais versionné, contenant les objets `admin`, `client`, `clientB`, `driver` avec `email` et `password`. `PERF_BASE_URL` vaut par défaut `http://127.0.0.1:3110`. Pour le navigateur, `PERF_PLAYWRIGHT_MODULE` indique le module Playwright installé ; `PERF_BROWSER_EXECUTABLE` indique Chrome (chemin macOS par défaut). Les tests ont utilisé le runtime Playwright déjà installé par Codex.

1. Arrêter uniquement le serveur de test dont on est propriétaire. Construire avec `npm run build` hors serveur dev. Lancer temporairement `npm run start -- -p 3110` pour les mesures production.
2. `node scripts/perf/measure-api.cjs outputs/perf01/prod-api-after.json production` : connexion puis deux passages séquentiels sur les routes des trois rôles. Premier passage = première utilisation de la route dans ce processus ; second = route et connexions chaudes. Les appels sont isolés de la recette navigateur.
3. `node scripts/perf/measure-browser.cjs outputs/perf01/prod-browser-after.json production` : connexion UI, navigation directe puis clic rapide depuis la page d'accueil. `readyMs` attend le titre du contenu ou la carte Leaflet puis 250 ms de stabilisation ; le navigateur conserve son cache HTTP, tandis qu'une navigation directe reconstruit son cache React Query. Ne pas confondre ce scénario de clic rapide avec le retour dans une page déjà chargée.
4. `node scripts/perf/measure-warm.cjs outputs/perf01/prod-warm-after.json` : aller/retour interne après chargement complet, deux échantillons par destination, deux images de rendu de stabilisation, sans attente artificielle de 250 ms.
5. `node scripts/perf/measure-mutation.cjs outputs/perf01/prod-mutation-after.json production-after` : crée **une nouvelle commande identifiée PERF01**, sans livraison ni facture ; mesure son annulation et sa lecture fraîche, vérifie 401/403/404 ; le `finally` nettoie uniquement cette commande avec triple garde id/référence/notes. Aucun objet préexistant n'est supprimé.
6. `node scripts/perf/verify-browser.cjs` : nouvelle commande PERF01-UI ; annulation par le menu réel admin, disparition de la liste client déjà ouverte après revalidation, barre de progression sur réponse volontairement retardée. Même nettoyage limité à la fixture. Captures et résultats dans `outputs/perf01`.
7. Après arrêt du serveur production, lancer temporairement `WATCHPACK_POLLING=true npm run dev -- -p 3110` et répéter les commandes API/navigateur avec fichiers `dev-…`. Le polling du watcher contourne l'erreur EMFILE/404 observée dans le contexte d'exécution macOS ; il n'affecte pas la logique applicative. La compilation à froid est visible séparément dans le journal Next.
8. Arrêter les serveurs de test en fin de recette.

Diagnostics sans mutation métier : `measure-auth-database.cjs` compare les anciens allers-retours avec la jointure native sur la même connexion ; `verify-joins.cjs` compare les objets et le curseur d'export ; `node --import tsx scripts/perf/verify-statistics.cjs` compare anciens compteurs et agrégats sur les données présentes. `snapshot-business.cjs <sortie.json>` enregistre seulement nombres de lignes et empreinte, en excluant user.lastLoginAt/updatedAt modifiés normalement par la connexion.

Le client Prisma doit être généré (`npm run db:generate`, génération locale uniquement). Le drapeau `relationJoins` change la stratégie client, aucune migration SQL. Les instantanés des fichiers avant PERF-01 et le patch limité à cette tâche sont archivés avec les preuves ; le build avant utilise un client Prisma distinct sans relationJoins afin de ne pas mélanger les stratégies.

Le pool applicatif est borné à **5 connexions par instance**, également en production. Une valeur `connection_limit` déjà présente dans DATABASE_URL est conservée si elle respecte aussi la borne 1…10. `DATABASE_CONNECTION_LIMIT=1…10` permet une surcharge explicite et validée. En hébergement, compter jusqu'à `5 × nombre d'instances` clients de pool, plus les workers/scripts ; adapter cette limite au pool Supabase et refaire les mesures avant publication. Cette recette ne valide pas la charge multi-instance ni un dimensionnement hébergé. `DATABASE_CONNECTION_MODE=session` est un choix explicite limité au pooler Supabase ; le mode transactionnel reste le défaut et garde `pgbouncer=true`.

La liste des missions fournit désormais un lien photo applicatif privé sans attendre Storage. Sur le build final, `node scripts/perf/verify-proof.cjs` vérifie cinq lectures de liste, le propriétaire et les refus client/anonyme/autre mission ainsi que le cache privé. Ne jamais archiver l’URL signée. Après modification de code dans le contexte macOS décrit, redémarrer le serveur de test pour éviter une ancienne version HMR ; ne pas arrêter un serveur utilisateur.

Après toutes les recettes, exécuter `node scripts/perf/snapshot-business.cjs outputs/perf01/business-after.json`, puis `node scripts/perf/verify-budgets.cjs`. Le vérificateur compare les mesures finales aux budgets fixés dans `budgets.json`, la recette UI et la preuve privée, ainsi que l’empreinte métier avant/après. Les passages intermédiaires restent archivés et ne remplacent pas les mesures finales.
